# 의사결정 모니터 — 차콜 방향 V2

Day6 원본은 frontend/src, 예시는 frontend/fixtures/alerts.json이다. build_web.py는 외부 디자인 폴더 없이 실행 파일만 생성한다. 모의 조회는 src/mock-adapter.js, 렌더링은 src/app.js, 조회 상태·표시 매핑은 src/display-contract.mjs가 담당한다. entry.js는 브라우저 시작만 담당한다. 동적 식별자도 본문·속성에서 이스케이프하고, 인라인 JSON은 HTML 종료 문자를 유니코드 이스케이프로 보존한다. 판단·원문 데이터 자체는 변경하지 않는다.

상태: C2 선택 확정. 실제 운영 API 연결 및 출시 검증 전의 예시 데이터 기반 웹 미리보기다. 1차 후보와 C1은 비교 이력으로 보존한다.

## 확정 표시 계약 — C2

C2가 선택되었다. 목록·상세 분할, 차콜 디자인, 최신순/KST, 독립 필터와 예시 데이터 표시는 유지한다. 이번 변경은 예시 화면의 표시 계약이며 FastAPI·DB·core·인증은 연결하거나 변경하지 않는다.

- 한글 설명은 `rule_id + evidence`의 명시적 매핑이다. `evaluation_integrity_override / error_code=timeout_01` 단일 신호의 목록·상세 요약은 “평가 대상의 응답 시간 초과가 보고되었습니다.”, 신호 설명은 “입력된 실패 코드가 응답 시간 초과를 나타냅니다.”다. 모니터 서비스 장애나 직접 관측으로 설명하지 않는다.
- `latency_high`의 숫자형 `latency_ms` 설명은 “입력된 지연 시간이 평가 기준을 초과했습니다.”다. API 처리 시간이 아니다. 정의되지 않은 실패 코드·규칙·근거 조합은 서버 사유 원문을 사용한다. 승인 신뢰도와 모델 버전 누락은 해당 규칙과 근거 값이 일치할 때만 기존 한글 매핑을 사용한다. 점수·수준으로 사유를 생성하지 않는다.
- level, human_required, risk_score, uncertainty_score, recommended_actions는 응답 값을 그대로 표시한다. 점수는 범주별 신호 점수 합계이고, 프론트에서 재판정하지 않는다. 권장 조치는 실행 완료가 아니다.
- 원문 펼치기는 reason_summary 또는 signal.reason만 표시한다. GET에서 제외된 alert/signal metadata의 항목이나 열람 기능은 없다.
- null은 “입력값 없음”과 원래 `null`을 함께 표시한다. `0`, `false`, `""`는 원문 그대로이며 누락 취급하지 않는다. 빈 evidence는 “표시할 판단 근거가 없습니다.”, 빈 signals는 “발동된 평가 신호가 없습니다.”, 빈 recommended_actions는 “제공된 권장 조치가 없습니다.”다. DB 원본이나 안전 여부를 단정하지 않는다.
- 로딩: “Alert를 불러오는 중입니다.” / 성공한 빈 목록: “현재 조회 조건에 맞는 Alert가 없습니다.” / 상세 404: “해당 Alert를 찾을 수 없습니다.” / 요청 실패: “Alert를 불러오지 못했습니다.”와 다시 시도 / 필수 필드·타입 오류: “응답 데이터를 확인할 수 없습니다.”로 구분한다. 누락값을 0·false·빈 배열로 대체하지 않는다.
- 다른 상세 요청이 시작되면 이전 내용을 즉시 비운다. 이전 요청의 늦은 응답은 무시한다. 필터 결과에서 선택 항목이 제외되면 상세를 비운다.
- 조회 상태는 예시 어댑터로 확인한다. 테스트용 `?preview=` 시나리오는 화면 메뉴나 API 응답 필드가 아니다. 실제 GET /alerts 및 GET /alerts/{alert_id}의 네트워크·인증·페이지네이션·서버 오류 통합 검증은 추후 연결 시 수행한다. 전체 건수·총 페이지는 추가하지 않는다.

## 1. 분위기와 업무 목적

### INFO 표시 규칙

INFO는 중립적인 색상과 원문 `INFO`를 사용하는 서버의 평가 수준이다. 안전 보장이나 완료 상태가 아니다. `human_required`는 수준과 독립적으로 응답 그대로 표시하고, 모든 수준에 동일한 점수·신호·근거·권장 조치 구조를 사용한다.

`missing_model_version` 단일 신호와 `evidence.model_version=null`이 일치하면 요약은 “입력된 모델 버전 정보가 없습니다.”다. 이 매핑은 INFO 여부와 무관하며, 대응하는 정의가 없으면 서버 사유 원문을 유지한다. “발동된 평가 신호가 없습니다.”는 상세의 `signals=[]`에만 표시하며 INFO 공통 사유로 사용하지 않는다. 정보 보완과 즉각적인 조치 요구 없음이 함께 제공돼도 원래 순서대로 모두 표시한다.

`evt_info_missing_019`는 모델 버전 누락만 발생한 재현 입력의 core 출력에 맞춘 예시다(INFO, 검토 요구 없음, 위험 0, 불확실성 1, null 근거, 두 권장 조치). 평가 사유 원문은 `risk remains low, while uncertainty is present; action-level caution is recommended`이며, 입력 사실의 한글 설명과 별도로 보존한다. 예시 식별자·생성 시각은 합성이며 실제 GET 응답을 검증한 것은 아니다. 프론트는 INFO의 검토 여부를 결정하지 않는다.

내부 운영자가 검토할 Alert를 찾고 평가 이유와 근거를 읽는 도구다. 낮은 채도의 차콜, 일정한 구분선, 정렬된 원문 필드가 중심이다. 마케팅 문구, KPI 카드, 장식, 가상 내비게이션을 사용하지 않는다.

C1은 기존 C의 테이블·상세 분할을 유지한다. 54:46 비율에서 생성 시각, event_id, level, human_required, 사유 요약을 독립된 열로 비교한다. C2는 40:60 비율에서 사유를 우선 읽고 식별자·시각을 부차적으로 확인하며 상세 근거에 더 넓은 공간을 배정한다. 두 안 모두 최신 생성순이다.

검토 요구는 사람 아이콘+‘검토 필요’, 대시 아이콘+‘검토 요구 없음’으로 별도 표시한다. 수준의 빨간색을 검토 여부에 중복 적용하지 않는다. 색상을 지워도 의미를 읽을 수 있어야 한다.

## 3. 타이포그래피

한국어 Pretendard 1.3.9, 영문 Geist, 코드·식별자 Geist Mono. 사유 13–15px, 상세 주요 사유 22–25px, 섹션 제목 14px, 기술 정보 11–12px. 최소한의 글자 크기 차이로 업무 정보의 우선순위를 만든다. 장문의 한국어 사유는 keep-all과 충분한 행간으로 읽고 식별자는 원문을 유지한다.

현재 검토용 화면은 CDN 글꼴을 사용한다. 실제 구현 단계에서는 라이선스를 확인하고 필요한 파일만 자체 호스팅한다. 웹폰트가 실패하면 시스템 sans-serif/monospace로 표시된다.

## 4. 컴포넌트와 데이터 의미

- native select 필터: level과 human_required는 독립적이다. 두 조건은 AND 결합이다.
- 항목 상세 버튼: event_id가 포함된 접근 가능한 이름과 44px 클릭 영역. 선택된 행은 배경+좌측선+aria-current로 구분한다.
- 평가 사유: 상세 최상단에 전체 한국어 요약. 원문 reason_summary는 펼쳐 읽는다.
- 점수: risk_score/uncertainty_score를 별도 숫자로 표시한다. 정수 합계이며 확률·백분율·게이지를 사용하지 않는다. override 사례는 점수와 관계없이 CRITICAL이 될 수 있음을 설명한다.
- signals: rule_id와 category, 사유, 원문, evidence, signal score 및 override 적용을 구분한다. evidence JSON 값은 문자열 인용부호·null·숫자를 보존한다.
- 권장 조치: 번호와 한국어 조치명, 원문 action code. 읽기 전용 목록이다.
- 추적 정보: event_id, 생성 요청 trace_id, 생성 시각 KST, alert_id. 조회 요청의 trace와 혼동하지 않는다.
- 필터 결과 없음: 조건 변경 안내. 신호 없음: 데이터가 빈 상태임을 직접 표시한다.

프로토타입 데이터는 여섯 합성 재현 입력으로 확인한 예시다. 이관 기준 core는 같은 저장소 main a829ac48e3ddac471977d4556ee785af473eb19e이다. 운영 데이터가 아니다. /alerts 조회 API에 연결된 것처럼 보이는 동작을 추가하지 않는다.

## 5. 그리드와 화면 크기

1440px 데스크톱을 주 검토 크기로 한다. 상단 56px, 목록 여백 24–26px, 상세 여백 30–40px. 상자 안에 상자를 반복하지 않고 섹션 사이의 선과 여백으로 구분한다. 점수는 카드 두 개 대신 하나의 행을 공유한다. 권장 조치는 별도 카드 버튼이 아닌 평면 목록이다.

1100px 이하에서는 목록 다음에 상세가 이어지는 1열 배치다. 767px 이하에서는 테이블 행도 정보 블록으로 전환한다. 실제 운영 버전에서 패널별 스크롤과 목록 상태의 URL 복원은 구현 단계에서 결정하고 검증한다.

## 6. 인터랙션과 접근성

필터 변경, 항목 선택, 닫기, 원문 펼치기만 제공한다. 레이아웃과 대비로 즉시 확인하며 불필요한 애니메이션은 없다. focus-visible 외곽선, label/select 연결, semantic table 및 heading, icon aria-hidden을 사용한다. reduced-motion 환경에서 전환을 제거한다.

운영 API 연결, 인증, 오류 및 로딩, 페이지네이션, 실제 브라우저·접근성 전수 검증은 후보 승인 이후 수행할 범위다. 디자인 후보의 동작 검증을 운영 출시 검증으로 표현하지 않는다.

## 7. 금지 패턴과 참고 근거

무신호 INFO의 reason_summary가 정확히 `risk signals remain low and do not require escalation`인 경우 목록·상세 표시를 “현재 평가 기준에서 위험 신호 수준이 낮게 분류되었습니다.”로 매핑한다. 서버 원문은 사유 원문 보기에 보존하며, 다른 원문이나 INFO 전반에 이 설명을 적용하지 않는다. human_required 및 권장 조치는 응답 그대로 유지한다.

`approve_confidence_low`와 `latency_high` 두 신호와 정의된 근거 조합의 요약은 “낮은 신뢰도의 승인 판단과 입력 지연의 기준 초과가 확인되었습니다.”다. `timeout_01` 실패 코드의 응답 시간 초과와 구분한다.

안전·완료 상태, 처리 완료 버튼, 실시간 상태 점, 성능 차트, 전체 건수, 가상 사용자·설정 메뉴, 일괄 조치, 장식 그라데이션은 추가하지 않는다. WARN과 검토 요구 없음이 함께 나타나는 사례를 항상 확인한다.

Stitch 프로젝트에서 생성·수정한 C 화면을 출발점으로 삼고, ECC frontend-design-direction, design-system, frontend-a11y의 원칙에 따라 HTML/CSS를 직접 재구성했다. V2가 Stitch에서 재생성된 결과라고 주장하지 않는다.

실무 제품의 목록과 근거 읽는 방식을 확인한 공식 참고자료:
- [Linear Triage](https://linear.app/docs/triage): 목록과 선택한 항목을 오가는 검토 흐름.
- [Sentry Issue Details](https://docs.sentry.io/product/issues/issue-details/): 이유와 진단 근거를 구분하는 상세 정보 구조.
- [Datadog Manage Monitors](https://docs.datadoghq.com/monitors/manage/): 독립적인 필터와 목록 정보 정렬.

해당 제품에 있는 해결·담당자 배정·집계 기능을 이 서비스에 옮기지 않는다. 실제 API 계약과 사용자의 최소 요구사항이 우선한다.
